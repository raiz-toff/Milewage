## PR M3.3 — Restore with safety copy and automatic revert, POST /setup/restore (Server track)

- Done: `src/backup/restore.ts` (`createRestoreService`) and `POST /setup/restore` (multipart `file` + `recovery_key`, streamed to disk, 512 MiB, public but 409 `setup_already_done` once a user exists). Sequence: single-flight guard and server mode `restoring` (new `src/state.ts`; a hook answers every other `/api` request with 503 `restoring`, `Retry-After: 5`, except `/setup/status`) → decrypt with the recovery key and gunzip into `.restore-tmp/` → preflight on the copy (`integrity_check`, `foreign_key_check`, **abort without touching live data** if `schema_migrations` names a migration this build does not know, or on a wrong key or damaged file, which look the same to the caller: 422 `/recovery_key`) → an older backup is migrated forward **in the scratch copy** → safety copy of the live database as a `pre_restore` backup (skipped on a fresh host; if it fails the restore stops) → swap → verification output → resume. `RestoreVerification` has the 08 fields plus `instance_id` and `restore_generation`; the generation becomes `max(live before, restored) + 1` and the restored `instance_id` is kept. On a fresh host `config/secrets.json` is written from the key the driver supplied, so later backups open with the card they hold. Failed restores count against a limit of 5 per 15 minutes per client (429 with `Retry-After`). Caddy: the restore path gets `request_body` 512MB, every other API path keeps 2MB (limits moved from the site block into the handlers because the site-level limit capped the restore route as well); `infra/docker/smoke.sh` now uploads 3 MB of multipart through Caddy to the restore route and expects the API's 422, and passed (Docker 29.1.3).
- Deviation from `10` section 7 (on purpose, stated): the swap is **not** a file swap. The server holds one write connection and every repository captured it, so closing and reopening would leave dead handles. The verified, forward-migrated copy is `ATTACH`ed to the live connection and every table's rows are replaced in one transaction (foreign keys off for the copy, then `foreign_key_check` and `integrity_check` inside the transaction). The "auto-revert" is therefore a rollback: any failure, including the `verify` test seam, leaves the live database byte-for-byte logically unchanged, and the pre-restore backup remains on disk as the second safety net. Cost: for a very large database the whole replacement runs in one transaction (WAL grows to about the size of the data and the event loop is held; B8/B9 on the VM must show the time). The command-line `milewage-cli restore` for an instance that already has data is not built: the service supports it (`allowExisting`), but there is no CLI process or local control channel yet and no PR text asks for one.
- Tests: 10 new in `restore.test.ts` (fresh-host round trip through real multipart: counts, date range, generation 3 from 0 and 2, instance id and `X-MileWage-*` headers, login with the old owner, secrets written; 409 when a user exists; wrong key 422 ×5 then 429 and the host stays empty; damaged file, bad key text, missing key, non-multipart; **newer schema aborts**; an older backup (built from migrations without 0006) is migrated forward and restored; 503 `restoring` and the open status route; over live data a forced verification failure rolls back and leaves the safety copy; a successful restore over live data gives generation 8 from a live 7; the service refuses a populated instance without `allowExisting`).
